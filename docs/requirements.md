# 要件定義：多目的最適化（ε制約法）輸送計画 Web アプリ

> 実装を始めたあとに、課題の要件と実装の内容を整理するために書いた要件定義である（後付け）。
> 問題の詳細は [problem.md](problem.md)、アプリの使い方は [app_summary.md](app_summary.md) を参照。
> 各要件の状態は「済」（実装・動作確認済み）、「予定」（未実装）で示す。

## 1. 背景と目的

- **背景**：港から配送センター（DC）への輸送では、トラック（速いが高く CO2 が多い）と鉄道（安く CO2 が少ないが遅い）のどちらを使うかで、コストと所要日数がトレードオフになる。単一の「最適解」はなく、どこまで払ってどこまで速くするかは意思決定者が選ぶ必要がある。
- **目的**：コストと平均所要日数のパレートフロントを求め、意思決定者が解を選んで地図で確かめられる Web アプリを作る。条件が変わったとき（What-if）にトレードオフがどう変わるかも試せるようにする。
- **元の教材**：MIT SCM.275x「Multi-Objective Optimization - Epsilon Constraint Method - Exercise」（09。後半の問題）。

## 6. What-if 分析と可視化の強化（追加要件）

### 6.1 What-if シナリオ（P1）

基準の入力にシナリオを当てて計算する。最適化モデルは変えず、入力値だけを変える。

| ID | シナリオ | 入力の変え方 | 状態 |
|---|---|---|---|
| W1 | 港の停止（ストライキ） | その港の供給量を0にし、ほかの港へ供給量の比率で振り替える。地図では灰色で示す | 済 |
| W2 | 需要の増減 | 需要を ×1.2／×1.5／×2 にし、供給量も同じ倍率にする | 済 |
| W3 | 燃料の高騰 | 道路の単価を ×1.3／×1.5 にする | 済 |
| W4 | 鉄道の遅延 | ターミナルでの滞留に +1.5日／+3日 | 済 |
| W6 | シナリオで計算した結果には、適用したシナリオを見出しに表示する。全港を停止するなど計算できない組合せは理由を表示して止める | 済 |

**設計上の判断**：供給の合計と需要の合計がちょうど同じ（15,000 t）なので、港を止めたり需要だけを増やしたりすると解がなくなる。そのため、港の停止は「ほかの港へ振り替え」、需要の増減は「供給量も同じ倍率」とした。

## 7. 対象外

- 鉄道ターミナルの選択（各 DC は測地線距離で最も近い1か所に固定。元問題どおり）
- 輸送量の整数化（トラック・コンテナ単位）
- CO2 を第3の目的にした3目的最適化
- Web への公開（デプロイ）

## 8. 受け入れ基準

1. 初期値で「計算」すると、ユートピア点 (\$1,311,311, 2.50日)、ナディア点 (\$1,812,413, 5.32日) が表示される。
2. ε = 0.5（主目的＝平均所要日数）で \$1,561,862・3.38日・CO2 2,386 t になる。
3. スライダーを動かすと、地図と数値が待ち時間なしで切り替わる。
4. 各 What-if シナリオで計算でき、結果の見出しにシナリオが表示される。シナリオをすべて「なし／×1」に戻すと基準と同じ結果になる。
5. 入力が不正なとき、計算ボタンが押せず理由が表示される。
